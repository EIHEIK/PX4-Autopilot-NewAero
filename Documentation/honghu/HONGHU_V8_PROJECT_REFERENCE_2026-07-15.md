## 4. 项目需求和已经确认的工程决策

对话中已经确认的需求应视为 V8 后续验收契约：

1. 基于 PX4 架构和 Gazebo 环境建立独立的 honghu_wing_150kg_v8。
2. 优先保证坐标、舵偏符号和气动力模型正确，不能沿用 V7 中存在疑问的气动公式。

   - 不参与常规俯仰控制分配；

7. 气动力模型是当前最重要部分；动力模型允许阶段性简化，但当前代码已经实现表格动力模型。
8. 旧模型只作参考，不能因为旧文档或旧公式存在就默认其正确。
9. 地面范围必须按当前 world 文件核查，不能继续沿用“约 1 km 地面”的旧推断。

## 6. 坐标系和符号契约

### 6.1 三套坐标

| 坐标系 | 轴方向 | 用途 |
|---|---|---|
| PDF/PX4 机体系 FRD | X 前、Y 右、Z 下 | 气动角、机体系力矩、PX4 控制 |
| Gazebo 模型局部系 FLU | X 前、Y 左、Z 上 | SDF 链接、关节、局部力和力矩 |
| Gazebo 世界系 ENU | X 东、Y 北、Z 上 | 世界位置、姿态、地面和任务 |

FRD 到 Gazebo FLU 的向量转换为：

~~~text
R = diag(1, -1, -1)
v_GZ = R v_FRD
~~~

PDF 中以机头为坐标原点的点，转换到以质心为原点的 Gazebo 模型局部坐标：

~~~text
p_GZ = (x_PDF + 1.57, -y_PDF, -z_PDF)
~~~

气动力矩先按 FRD 定义计算，再只转换一次：

~~~text
M_FRD = qbar S [ b Cl, cbar Cm, b Cn ]
M_GZ  = [ Mx_FRD, -My_FRD, -Mz_FRD ]
~~~

因此：

- 正滚转系数 Cl → Gazebo +Mx；
- 正俯仰系数 Cm（抬头）→ Gazebo −My；
- 正偏航系数 Cn（向右偏航）→ Gazebo −Mz。

### 6.2 惯量转换

PDF 给出的 FRD 惯量为：

~~~text
Ixx=25.86, Iyy=39.14, Izz=59.12
Ixy=-0.017, Ixz=-3.520, Iyz=-0.0019 kg·m²
~~~

按 I_GZ = R I_FRD Rᵀ 转到 FLU 后，非对角项为：

~~~text
Ixy=+0.017, Ixz=+3.520, Iyz=-0.0019 kg·m²
~~~

model.sdf 中 base_link 本体的质量为 149.16 kg，惯量也略小于总目标；八个舵面、轮子和前轮叉等子链接组装后，整机闭合到 150 kg 和上述总惯量。不能只读取 base_link 的单独惯量就判断模型错误。

### 6.3 气动角

相对气流先从 Gazebo FLU 转为 FRD，然后：

~~~text
alpha = atan2(w, u)
beta  = atan2(v, sqrt(u²+w²))
~~~

### 6.4 关节角与 PDF 虚拟舵偏

V8 同时保留两层定义：

- θjoint：Gazebo 关节绕 SDF axis 的右手角；
- δdoc：气动查表使用的 PDF 虚拟舵偏。

正关节角对应几何动作：

| 关节 | θjoint>0 |
|---|---|
| 左/右副翼 | 后缘向上 |
| 左/右升降舵 | 后缘向上 |
| 左/右方向舵 | 后缘向飞机右侧 |
| 左/右鸭翼 | 后缘向下 |

虚拟舵偏合成为：

~~~text
δa_doc = 0.5 × (-θ左副翼 + θ右副翼)
δe_doc = 0.5 × ( θ左升降舵 + θ右升降舵)
δr_doc = 0.5 × ( θ左方向舵 + θ右方向舵)
δc_doc = 0.5 × ( θ左鸭翼   + θ右鸭翼)
~~~

正舵偏的主效应：

| δdoc | 几何动作 | FRD 主力矩 | Gazebo 主力矩 |
|---|---|---|---|
| δa_doc>0 | 左副翼下、右副翼上 | +Mx，右滚 | +Mx |
| δe_doc>0 | 升降舵上偏 | +My，抬头 | −My |
| δr_doc>0 | 方向舵后缘向右 | +Mz，右偏 | −Mz |
| δc_doc>0 | 鸭翼后缘下偏 | +My，抬头 | −My |

这也回答了“正舵偏是否通常产生负力矩”的疑问：舵面几何正方向本身没有跨项目统一定义。V8 明确把 δdoc 正方向定义成产生正 FRD 主力矩；转换到 Gazebo FLU 后，正俯仰和正偏航分别表现为负 My、负 Mz。不能只看 PWM 或单个 joint angle 判断符号。

## 8. V8 气动力模型

### 8.1 总体原则

V8 使用独立 HonghuAeroV8 插件，不复用 V7 气动力公式。计算链为：

1. 读取 base_link 相对气流和角速度；
2. FLU→FRD；
3. 计算 α、β 和动态压；
4. 插值静态六分量系数；
5. 加入四类舵面贡献；
6. 加入 p、q、r、αdot、βdot 动导数；
7. 处理低速、数据边界和失速扩展；
8. 在 FRD 计算力和力矩；
9. 单次转换为 Gazebo FLU，再转到世界系施加。

### 8.2 静态表

- CL/CD/Cm 对 β 采用偶对称；
- CY/Cl/Cn 对 β 采用奇对称；
- 表内使用双线性插值；
- α=18°、20°缺失的非零 β 数据，用 α=16°的 β 增量形状补全，并标为 derived；
- 文档区间外采用连续 Viterna 扩展；
- 负迎角扩展锚点和补全数据属于工程推导，不应冒充 PDF 原始数据；
- β 超过 ±16°时钳位并设置诊断标志。

### 8.3 舵效表解释

当前实现为：

~~~text
ΔCi = Di(α, β, δdoc) × δdoc_deg
~~~

其中 Di 是在 PDF 给定舵偏切片之间插值得到的局部每度导数。δdoc=0 时总舵效严格为零，但导数表本身无需在 0°处人为置零。

各舵面边界处理：

- 升降舵：在 −10°、+10°、+20°数据间插值；机械范围 ±30°，超出表范围保持最近导数并乘实际角度，设置外推标志。
- 副翼：以 +10°表为局部导数，负方向按有符号角度反向；源数据迎角主要在 0°～12°，高迎角逐渐衰减。
- 方向舵：以 +10°表为局部导数，负舵偏使用反射；源数据主要在 α=0°～8°、β=±12°。
- 鸭翼：−4°～+8°内查表；+8°～+15°有界外推；小于 −4°时将有效气动舵偏冻结在 −4°，避免把 −50°机械刹车位置线性放大成非物理力矩。
- 鸭翼局部有效迎角约在 12°后衰减，到 16°附近失去当前线性舵效，与 PDF“鸭翼易失速”的说明保持一致。

PDF 明确说明：

- 鸭翼安装角 0°；
- 配平舵偏约 +4°；
- 鸭翼只作配平，俯仰机动由后翼升降舵完成；
- 起飞时快速到达预定鸭翼偏角；
- 鸭翼失速后舵效丧失。

### 8.4 动导数

当前代码使用：

~~~text

CYp          = -0.15
CYr          = +0.34
Clp          = -0.33
Clr          = +0.10
Cmq          = -7.0
Cm_alpha_dot = -0.33
~~~

αdot 和 βdot 使用实际角度时间导数，不再把 Cm_alpha_dot 或 Cn_beta_dot 错乘 α、β。低于 3 m/s 时重置角度导数，3～5 m/s 平滑启用动态项，防止滑跑初期数值尖峰。角度导数采用约 0.05 s 滤波并限制原始尖峰。

## 9. 动力模型

HonghuPropulsionV8 是当前唯一推力源。

输入和处理：

- ESC 输入统一为 0～1000；
- 按高度、油门/转速和来流速度插值 PDF 表格；
- 推力从 kgf 转为 N；
- 同时插值并发布 RPM、反扭矩和燃油率；
- 油门上升/下降时间常数为 0.5/0.3 s；
- 表格中的负推力和负扭矩点保留为高速风车工况。

发动机安装：

~~~text
PDF 机头坐标：(-2.80, 0, -0.12) m
Gazebo 质心坐标：(-1.23, 0, +0.12) m
Gazebo 推力方向：[cos(3°), 0, -sin(3°)]
~~~

这里的 3° 已经进入运行时代码，不是仅保留在参数说明中。Gazebo 使用 FLU，
所以方向向量的负 Z 分量表示向下；转换到 FRD 后为
`[cos(3°), 0, +sin(3°)]`。插件先计算该方向上的推力，再计算
`M = r_engine × F + M_reaction`，最后把力和力矩作为 world wrench 施加到
`base_link`。以海平面、100% 油门、40 m/s 表格点的约 316.5 N 推力为例，
向下分力约 16.6 N，作用点产生约 +17.6 N·m 的 Gazebo My，即约
−17.6 N·m 的 FRD 俯仰力矩（低头）。因此发动机安装耦合会真实进入俯仰闭环。

插件同时施加：

1. 推力作用点相对质心产生的力矩；
2. 螺旋桨反扭矩。

当前仍固定整机质量为 150 kg。燃油率只用于诊断，不更新质量、质心和惯量。这是已知简化，而不是遗漏。

## 10. PX4 通道、鸭翼和起飞控制

### 10.1 舵机映射

桥接器已从 8 路扩展到 9 路：

- 8 路气动舵面；
- 第 9 路鼻轮转向。

新增 SIM_GZ_SV_ZMAP：

- 0：保持旧模型的传统对称映射；
- 1：使用 MINA/ZEROA/MAXA 三点分段线性映射。

V8 开启 ZMAP，以支持鸭翼 −50°/0°/+15°的不对称机械行程。传统舵面为 ±30°，鼻轮为 ±30°且通过 MINA9=+30、MAXA9=−30 完成所需符号翻转。

### 10.2 鸭翼逻辑

控制分配中 LeftCanard/RightCanard 的三轴 torque effectiveness 被强制置零，因此鸭翼不参与俯仰、滚转或偏航闭环解算。

鸭翼由独立 canard_setpoint 状态机叠加：

~~~text
中立：FW_CANARD_NEUT = 0.5
起飞/巡航：NEUT + 0.5 × FW_CANARD_TO
气动刹车：NEUT - 0.5 × FW_CANARD_BRK
~~~

V8 参数：

~~~text
FW_CANARD_NEUT = 0.5
FW_CANARD_TO   = 0.266667
FW_CANARD_BRK  = 1.0
~~~

在 −50°/0°/+15°分段映射下，起飞/巡航命令对应约 +4°后缘下偏。

当前状态机行为：

1. 地面早期保持中立；
2. 跑道起飞状态达到 CLIMBOUT 时锁存 deployed；
3. 正常空中飞行继续保持约 +4°；
4. 着陆触地条件可进入刹车；
5. 后续可锁存收回。

这与用户最终确认的 V3 思路一致。它不是“只在起飞和降落偏转”，而是“起飞时展开，空中继续保持固定配平偏转，且不参与俯仰分配”。

V3 与 V8 的数值命令不能直接逐项比较：V3 使用过旧的对称舵机映射，V8 使用不对称真实机械行程；一致的是状态机思想，不是归一化输出数值。

地面和空中俯仰控制不是两套完全独立的控制器：`FW_PR_FF_RWTO` 与
`FW_PR_RWTO_Q` 是跑道阶段专用前馈及其释放条件，而 P/I/D/FF、姿态外环

`FW_T_I_GAIN_PIT=0.05` 用于 TECS 俯仰能量误差消除。积分器未被禁用；
`FW_PR_IMAX=0.12` 仅限制其最大配平权限，避免反向机动时残余积分主导舵量。

空中横向控制与跑道方向控制也不是同一组制导参数：`NPFG_PERIOD=20 s` 作用于
空中航迹响应，而 `RWTO_NPFG_PERIOD=8 s` 仍用于跑道转向。最终默认滚转指令上限为
30°，40 m/s 无风协调转弯半径约 283 m。任务中的不连续反向折线仍不能依靠提高
控制增益变成可瞬时完成的指令；最终验收使用每段 1200 m、连续 30°改航且不折返的路线。

需要注意参数持久化：

- 4028 中有些参数使用 param set；
- 有些使用 param set-default；
- 已有 parameters.bson 可能保留旧值并覆盖 set-default 的预期。

每次正式复现都应保存实际参数快照，不能只引用机架文件。需要重置参数时应明确操作目的，避免误删其他机型参数。

### 12.9 当前步长与 Gazebo 桥容量结论（2026-07-16 修订）

- V8 当前生产和验收步长为 **2 ms（500 Hz 物理）**。
- 在 0.5/1 ms 下，Gazebo 每个物理 tick 发布 clock/pose，消息速率超过当前 SITL
  `GZBridge` 的实时消费能力；Gazebo 真值会比 PX4 本地状态前进数十至数百米，控制器
  因而对过期状态动作。这是消息容量/时序问题，不是模型在更细积分步长下物理发散。
- V8 的 pose 订阅当前限制为 250 Hz；传感器和 pose 使用消息头仿真时间作为
  `timestamp_sample`，clock 在 V8 中按仿真时间以 2 ms 间隔更新。旧模型不启用 V8
  pose 限速，正常 QGC MAVLink 高速流也不受自动验收的最小流配置影响。
- 2 ms 下连续两次完整起飞均通过，PX4/Gazebo 在抬轮和离地点的位置差约 3～5 m；
  最终无覆盖起飞、五航段路线和持续盘旋均稳定。
- 若未来必须恢复 0.5/1 ms，不应直接把机架默认值改回去；应先把 clock/pose 处理移到
  可承受更高消息率的架构，或证明降低 real-time factor 后状态不再积压，再重新做收敛试验。

### 12.12 2026-07-16 二次复核：单独增大 NAV_ACC_RAD 为何仍像“过点转弯”

用户截图 `屏幕截图 2026-07-16 190251.png` 显示飞机仍接近航点后才明显改航，
`屏幕截图 2026-07-16 190540.png` 所示的目标则是在航点前进入连续圆滑转弯。对应最新
ULog `log/2026-07-16/10_59_03.ulg` 时长约 262.3 s、无 dropout。日志初始
`NAV_ACC_RAD=250 m`，57.284 s 的参数事件记录的手动值是 **400 m**，不是
500 m。任务管理器随后确实在距中间航点约 397.6～399.6 m 时提前切换，
因此 `NAV_ACC_RAD` 本身已经生效。

问题位于 Navigator 与固定翼位置控制器的两层切换逻辑：

1. `Navigator::get_acceptance_radius()` 对固定翼返回
   `max(NAV_ACC_RAD, position-controller acceptance radius)`；
2. Navigator 提前切换后，新位置设定中的 `previous` 是旧航点、`current` 是下一
   航点；
3. `FixedwingPositionControl::navigateWaypoints()` 检测到飞机仍在旧航点前方，
   且距旧航点大于 `_npfg.switchDistance(500)` 时，会继续调用
   `navigateWaypoint(old_waypoint)`；
4. NPFG 的距离定义为
   `min(500 m, track_error_bound × NPFG_SW_DST_MLT)`。

本日志的 NPFG `track_error_bound` 约 319～384 m，当时默认
`NPFG_SW_DST_MLT=0.32`，所以位置控制器的实际切换距离只有约 **102～123 m**。
这完整解释了“任务已在 400 m 接受，飞机却仍几乎飞到旧航点”的现象。单独
把 `NAV_ACC_RAD` 从 250 m 增加到 400 m 或 500 m，只会让 Navigator 更早更新
任务序号，不会消除这个 102～123 m 的内层限制。

为验证这个机理，首先进行了以下探针设置：

~~~text
NAV_ACC_RAD       = 250 m
NPFG_SW_DST_MLT   = 0.90
~~~

在同类飞行状态下，该设置的 NPFG 内部切换距离预计约为 **288～345 m**，与
40～45 m/s、30°坡度时约 290～350 m 的协调转弯半径同量级。

本次已完成静态契约检查和 PX4 ROMFS 构建，且启动输出确认
`NPFG_SW_DST_MLT: 0.3200 -> 0.9000` 与 `NAV_ACC_RAD: 400.0000 -> 250.0000`
已实际加载。但两次自动动态回归在飞机解锁前因本机 UDP 心跳未进入验收脚本
而超时；其生成的 `log/2026-07-16/11_13_19.ulg` 和
`log/2026-07-16/11_16_29.ulg` 都是约 45 s 的未解锁启动日志，不得当作“最新飞行日志”。
随后在隔离 QGC 的本地/remote UDP 端口上完成了真正的 2 ms 动态 route 探针，
报告为 `analysis_outputs/honghu_v8_route_npfg_sw090_2ms.json`，ULog 为
`log/2026-07-16/11_21_11.ulg`。它证明 0.90 **确实提前切换，但不是正确的圆弧转弯**：

- 中间航点序号切换时距旧航点约 270.6～307.7 m；
- 无折返的 5 段任务全部完成，起飞仍正常：离地约 44.14 m/s、起飞最大真值俯仰
  8.19°、地面横向偏差约 0.039 m；
- 但航路横向 RMS/p95 上升到 51.71/112.25 m，稳态 RMS/p95 也上升到
  24.11/58.79 m；
- 最大实际滚转 33.55°，滚转跟踪 RMS 误差 6.70°，最低高度 32.63 m，因高度
  下限未通过而整体 FAIL。

根因是 `navigateWaypoints()` 提前切换后导航的对象是“下一条直线的无限延长线”，
而不是“当前航段与下一航段之间的切线圆弧”。在连续 30°左转测试中，飞机会先
尝试截获下一条直线的反向延长部分，再反向修正，因此新增 S 形而不是目标图的圆滑弧。

结论是拒绝 0.90，V8 当前恢复已验证的直线跟随基线：

~~~text
NAV_ACC_RAD       = 250 m
NPFG_SW_DST_MLT   = 0.32
~~~

若要精确重现目标图中的固定半径切线圆弧，下一步应在任务层根据“前一点—当前点—
下一点”生成 fillet/圆弧过渡航点，或在 PX4 位置控制中增加可关闭的 fillet 路径段。
不应再通过继续增大 `NAV_ACC_RAD` 或 `NPFG_SW_DST_MLT` 试图伪造该几何路径。

#### 运行时力矩平衡证据

当前地面三点姿态下迎角约为0°。以主轮轴线为转动支点，在FRD中采用：

- 质量150 kg，重量1471 N；
- 主轮轴 `x=-0.291274 m, z=+0.4551 m`；
- 鼻轮 `x=+0.924852 m`；
- 发动机点 `x=-1.23 m, z=-0.12 m`；
- 推力向下3°；
- 气动力和舵偏取恢复后报告中的运行时诊断值。

测得的轮载传感器数据。

这说明35 m/s附近不是没有控制命令：CLIMBOUT后升降舵很快达到约24.5°，已经接近
±30°机械行程，但主轮支点前方的质心产生约−429 Nm重量矩；发动机位于主轮轴上方，
向前推力又产生约−100～−190 Nm低头矩。气动抬头矩随动压增长，在约43 m/s以前
仍不足以可靠卸载鼻轮。接近零轮载后，接触刚度、轮胎几何和机体动态共同决定最终
开始抬头的精确时刻，随后升降舵因实际俯仰响应建立而回收。

当前气动模型在空中35 m/s并非完全“飞不起来”：离线配平在鸭翼+4°时可得到
`α≈6.85°、升降舵上偏≈3.93°` 的水平飞行解。区别在于地面三点姿态把迎角限制在
约0°，必须先满足绕主轮的抬头力矩平衡，才能建立该空中迎角和升力。

#### 当前根因判断与处理边界

最准确的结论不是“纯气动模型错误”，也不是“纯PID参数错误”，而是当前模型内部的
**地面抬轮力矩平衡限制**：

1. 主轮相对质心的位置决定重量低头力臂，是当前最大固定项；
2. 发动机相对主轮的高度和3°下倾推力线继续贡献低头矩；
3. 升降舵/鸭翼气动导数及0°地面迎角决定可用抬头矩；
4. PX4已经及时给出接近行程上限的升降舵，继续调触发速度、俯仰上限或积分器不会
   从根本上改变这个静态平衡。

日志与当前气动/几何计算在趋势和速度区间上自洽，说明仿真代码不存在明显的
“35 m/s有足够力矩却不执行”的控制链断路。但这不证明模型参数就等于真机：如果
PDF舵效表的“每度导数”解释、CAD主轮位置、实际质心或发动机安装点有误，44 m/s
仍可能是模型误差的结果。

下一步应按下列顺序核实，核实前不要为了追求35 m/s而任意移动起落架或放大舵效：

1. 用CAD/实机测量复核满载质心与主轮实际接地点，尤其是二者纵向距离；
2. 复核发动机推力作用点相对主轮的高度、3°方向定义和真实起飞推力；
3. 用CFD、风洞或舵面几何估算独立验证升降舵和鸭翼的 `Cm/deg`；
4. 若上述数据均正确，则接受约44 m/s抬轮，或作为构型问题评估主轮前移、提高
   俯仰操纵权限、分阶段油门/鸭翼策略；这些均需单独试验和全包线回归。

按当前模型粗略反算，若仅靠移动主轮而要求35 m/s、鸭翼+4°和接近满升降舵即可
抬轮，主轮轴需从 `x=-0.291 m` 前移到约 `x=-0.11 m`，量级约0.18 m。这是重大几何
改动，只能由CAD或真实构型支持，不能当作控制调参使用。

## 13. QGroundControl UDP 14550 历史故障与当前状态

### 13.1 已确认现象

PX4 启动正常：

- Gazebo world ready；
- V8 模型成功生成；
- MAVLink Normal 实例监听 WSL UDP 18570、默认远端 14550；
- PX4 最终显示 Ready for takeoff。

Windows 侧检查：

- Get-NetUDPEndpoint 未发现普通进程占用 14550；
- IPv4/IPv6 显示的 UDP 排除范围只有 50000–50059；
- 直接 Socket 绑定 UDP 14550 返回 AccessDenied / NativeError 10013；
- 使用相同代码绑定 UDP 15550 成功。

结论：在上述检查时刻，Windows 明确阻止本机进程绑定 14550。这是 Windows 网络、安全软件、Hyper-V/WSL NAT 或驱动层面的端口保护状态，不是 V8 模型、Gazebo 或 PX4 启动失败。

此前 QGC 能连接，说明该端口保护是环境状态变化，不代表项目代码回退。

### 13.2 推荐临时方案

不修改项目代码的优先方案：

1. 在 QGC 中关闭 UDP AutoConnect；
2. 新建手动 UDP Link；
3. QGC 本地监听端口设为 15550；
4. 远端目标设为 WSL 地址的 18570；
5. 若 Windows/WSL localhost 转发有效，可先试 127.0.0.1:18570；否则用 WSL 中 hostname -I 得到的地址。

QGC 从 15550 主动向 PX4 18570 发包后，PX4 MAVLink 会学习实际源端口并向该端点回复。

如果希望恢复默认 AutoConnect，再单独排查 Windows 的端口保护来源；不要为了绕过 14550 而修改气动、机架或 Gazebo 模型。

当前已经验证了本机Onboard UDP 14540脚本上传路径；用户随后也通过QGC完成了多次
正式任务飞行，说明当前QGC链路已经可用于仿真。由于没有记录这次QGC实际绑定的是
14550、15550还是系统自动恢复后的端口，准确状态应写成“14550曾被Windows阻止，
当前QGC任务链路可用，具体端口恢复机制未归因”，不能永久认定14550一定不可用，
也不能把它写成已查明的项目代码问题。

### 13.3 任务持久化、覆盖语义与修复

PX4 SITL 的机上任务保存在：

~~~text
build/px4_sitl_default/rootfs/dataman
~~~

它与 `parameters.bson` 是两套不同的持久化数据。QGC 自己保存的 `.plan` 文件也不
等于 PX4 当前机上任务；任何一侧存在副本都不能自动保证另一侧仍有任务。

此前 Gazebo lockstep 启动初期 `hrt_absolute_time()` 可能仍为 0。PX4 在启动时重发
已持久化任务，如果 `mission.timestamp=0`，Navigator 会把本来有效的任务视作无效。
当前 `src/modules/mavlink/mavlink_mission.cpp` 中的
`MavlinkMissionManager::update_active_mission()` 已加入保护：时间为 0 时写入
第一个有效时间戳1。历史21项任务的重启测试曾得到 `valid=true`、`land_index=19`；
修订后的当前任务为20项，两次正式QGC日志均得到 `valid=true`、`seq_total=20` 并
从序号0执行到降落项18。两类证据共同说明协议上传和早期启动重发问题已经修复。

仍需区分“任务没有保存”和“任务被工具主动替换”：

1. `run_honghu_v8_dynamic_acceptance.py` 在每次动态场景中先发送
   `MISSION_CLEAR_ALL`，再上传它自己的测试任务。
2. 当前脚本逐字节备份/恢复 `parameters.bson`、`parameters_backup.bson` 和
   `dataman`；测试结束后会恢复原任务，但异常退出后仍应人工核查。
3. `upload_qgc_plan.py` 默认以 `MISSION_COUNT` 事务式替换任务，完整上传并收到 ACK
   后将当前任务项复位为 0；只有显式指定 `--clear-first` 才会先清空机上任务。
4. 由 QGC 重新上传同名任务不是“恢复旧 dataman”，而是一次新的任务写入。

因此运行任何自动动态验收或上传工具前，都应先保存 `.plan` 源文件；如果需要保留
PX4 机上任务的原始状态，还应在 PX4/Gazebo 完全退出后备份 `dataman`。恢复
`dataman` 也必须在进程退出时进行，避免数据管理器仍在写文件。

1. 满载质心、主轮轴和实际接地点的CAD/实机坐标；

放大舵效。只有物理输入确认后，才选择接受约44 m/s、调整构型或设计新的起飞策略。

- 60 s 高度和空速包线。

如果 1 ms 起飞仍显著不同，应先比较 PX4 本地位置与 Gazebo 真值时间/位置差，再记录
前轮接触、升降舵角、俯仰角速度和 RunwayTakeoff 状态；不能把桥接积压误判为接触模型问题。

### 第六步：气动模型独立验证

气动力模型是项目核心，应使用至少一种独立来源验证：

1. CFD 或风洞的 CL/CD/Cm 基础曲线；
2. 舵偏扫描获得每度舵效；
3. 纵向配平点和静稳定裕度；
4. 侧滑下 CY/Cl/Cn；
5. 短周期和荷兰滚响应；
6. 实飞或高保真六自由度数据的系统辨识。

优先验证舵效表的“每度导数”解释和鸭翼失速处理。确认前不要把 −50°刹车力矩用于自动着陆安全判据。

### 第七步：最后处理着陆和高级地面模型

在起飞与巡航稳定后再依次加入：

1. 自动进近和拉平；
2. 触地判定；
3. 鸭翼刹车状态；
4. 地面减速和方向保持；
5. 必要时加入简化悬架；
6. 最后才考虑轮胎柔性和更复杂的地面接触。

### 18.3 为什么首次启动会打印大量参数变化

该现象在这次新工作区首次运行中是正常的。新仓库没有复制历史 `build/`，因此新的
`build/px4_sitl_default/rootfs` 起初没有可导入的 `parameters.bson`。`rcS` 根据模型名
找到 `SYS_AUTOSTART=4028`，发现已保存的机型号仍为0，于是临时设置
`SYS_AUTOCONFIG=1`、复位非保留参数、写入SITL传感器标定并加载4028机型参数。
终端因此逐项显示 `curr -> new`。

这不是每次启动都会重新清空参数。首次运行结束后的ULog实际参数为：

~~~text
SYS_AUTOCONFIG = 0
SYS_AUTOSTART  = 4028
FW_PR_P       = 0.40
FW_R_LIM      = 30
NPFG_PERIOD   = 20
NAV_ACC_RAD   = 250
SIM_GZ_SV_MINA9 = 30
~~~

同时已经生成约1.8 KB的 `parameters.bson` 和备份文件。后续以相同机型启动时会先导入
该文件，不应再次出现整套自动配置；若删除 `build/`、删除参数文件、切换机型，或在
QGC中请求恢复机型默认值，则可能再次出现。

必须区分4028中的两种写法：

| 写法 | 当前V8语义 | 对QGC调参的影响 |
|---|---|---|
| `param set NAME value` | 每次启动强制应用已验证的V8基线 | QGC可以在当次运行修改并保存，但下一次启动会被4028写回 |
| `param set-default NAME value` | 只改变该参数的机型默认值 | 已保存的QGC值通常可跨重启保留，除非执行参数重置/自动配置 |

当前4028有意用 `param set` 固化关键空速、TECS/俯仰、滚转、NPFG、航点半径、跑道
控制、舵机角度映射和鸭翼基线。因此，若以后希望QGC自动调参结果跨重启成为正式候选，
不能只在QGC点击保存：应先导出参数、记录ULog和试验条件，再经评审把选定值写入4028，
或者有意识地把相应行改成 `param set-default`。机械行程、通道映射和安全边界不建议为
方便临时调参而解除强制设置。
